# Зміни API для фронтенду — 19.10.2026

Остання чистка невикористаного коду не змінила клієнтський API. Нижче — зміни
сьогоднішніх бізнес-функцій. Усі шляхи вказано відносно базової адреси API.

## 1. Додавання страви: обов’язковий заголовок

`POST /orders/guest/items` тепер потребує `Idempotency-Key`.

- Генерувати один ключ на одну заплановану дію, рекомендовано UUID.
- При повторі запиту після таймауту використовувати той самий ключ і тіло.
- Інше додавання страви має отримати новий ключ.
- Без ключа або з некоректним ключем — `400`.
- Той самий ключ з іншим тілом — `409`.

Ключ: 1–128 латинських літер, цифр або символів `_.:-`. Повтор повертає поточне
замовлення без дублювання позиції. Потрібні чинні cookies гостя та відкрите замовлення.

## 2. Подача й оплата розділені

У позиції замовлення додано:

| Поле | Значення |
|---|---|
| `fulfillmentStatus` | `ORDERED`, `CONFIRMED`, `SERVED`, `CANCELED` |
| `paymentStatus` | `null`, `PENDING`, `SUCCEEDED`, `FAILED`, `EXPIRED` |
| `refundStatus` | `null`, `REQUESTED`, `PENDING`, `SUCCEEDED`, `FAILED`, `UNKNOWN` |

Старе `status` залишилося для сумісності. Для подачі використовуйте
`fulfillmentStatus`: `PAID_CARD` / `PAID_CASH` не означає, що страву подано.

Оплачену страву можна позначити поданою через наявний `PUT /orders/items/{id}`:

```json
{"orderItemStatusDto":"SERVED"}
```

Після підтвердженого повного повернення можна аналогічно передати `CANCELED`.
Запис про успішну оплату при цьому зберігається. Звичайне закриття замовлення
перевіряє оплату та подачу/скасування; ручне закриття залишається явною дією оператора.
Для історичних оплачених позицій подачу неможливо встановити автоматично:
міграція задає `fulfillmentStatus=CONFIRMED`.

## 3. Валюта та часовий пояс

Меню, замовлення й платежі повертають `currency` (`UAH` / `EUR`). Беріть валюту
з відповідного об’єкта, не з поточних налаштувань ресторану. У старих записах
валюта може бути `null`; такі суми не можна додавати до відомої валюти.

Ресторан повертає `timeZone`, типово `Europe/Kyiv`. Зміна адміністратором:

```http
PATCH /restaurant/this/time-zone
Content-Type: application/json
```

```json
{"timeZone":"Europe/Kyiv"}
```

Потрібна назва IANA, наприклад `America/New_York`; некоректні назви й фіксовані
зсуви відхиляються з `400`. Місячні звіти враховують пояс та літній час на бекенді.
Зміна поясу переінтерпретує межі історичних місяців, не змінюючи часові мітки.

Зміна регіону через наявний multipart `PUT /restaurant/this` потребує закритих
замовлень і query-параметра `confirmMenuPrices=true`. Ціни не конвертуються:
підтверджується їхнє числове значення в новій валюті. Часовий пояс не скидається.

## 4. Платежі, що потребують перевірки, і повернення

Нові адміністративні маршрути:

| Запит | Призначення / тіло |
|---|---|
| `GET /payments/reconciliation` | Список платежів, що потребують перевірки; пагінація |
| `POST /payments/{id}/invoice` | Прив’язати рахунок провайдера: `{"invoiceId":"..."}`; бекенд перевіряє належність, суму й валюту |
| `POST /payments/{id}/resolution` | `{"action":"CONFIRM_NOT_CHARGED","evidence":"..."}` або `ACKNOWLEDGE` після підтвердженого повернення |
| `POST /payments/{id}/refund` | Повне повернення разом із чайовими: `{"reason":"..."}` |
| `GET /payments/{id}/refund` | Стан повернення |
| `POST /payments/{id}/refund/sync` | Оновити стан; необов’язковий `?providerRefundId=re_...` для відновлення Stripe-повернення |
| `POST /payments/{id}/refund/retry` | Повторити лише підтверджено невдале повернення (`FAILED`) |

Для готівки в запит повернення додати `confirmCashReturned:true` лише після
фактичної передачі грошей клієнту. Повернення частини суми наразі немає.

**HTTP 200 не означає завершене повернення:** перевіряйте `data.status`.
При `PENDING` / `UNKNOWN` показуйте очікування або потребу перевірки; не запускайте
нове повернення автоматично. Повторний `POST /refund` повертає вже створену операцію.

`CONFIRM_NOT_CHARGED` доступне лише для невизначеної оплати без прив’язаного рахунку
після перевірки адміністратором у кабінеті провайдера; `evidence` обов’язкове.
Відомий рахунок у стані `PENDING` не можна вручну оголосити неоплаченим.

Наявний `POST /payments/{id}/sync` залишається доступним працівнику/адміністратору
для синхронізації відомого рахунку. Відповідь платежу містить, зокрема,
`method` (`CASH` / `ONLINE`), `currency`, `reconstructed`, `reconciliationIssue`,
`lastSyncError`, `resolutionNote`, `refundStatus`.

Невизначена онлайн-оплата блокує оплату готівкою, скасування відповідних позицій
та закриття замовлення з `409`. Не трактуйте таймаут як відмову оплати.

## 5. Звітність

`GET /admin/analytics/revenue-summary?year=2026&month=10` повертає:

- `currencies`: суми за кожною валютою — `cashRevenue`, `onlineRevenue`,
  `totalRevenue`, `onlineTips`, `paymentCount`, `orderCount`;
- `refunds`: `currency`, `refundedRevenue`, `refundedTips`, `refundCount`;
- `timeZone`, `unresolvedHistoricalPaymentsCount`,
  `reconciliationRequiredPaymentsCount`.

`currencies` містить надходження до вирахування повернень. Чиста виручка за місяць —
`totalRevenue - refundedRevenue` у тій самій валюті. Чайові рахуються окремо.
Повернення належить місяцю, коли бекенд уперше підтвердив його успіх, незалежно
від місяця продажу. Різні валюти не підсумовувати.

Наявний `GET /admin/analytics/monthly-summary` залишається безготівковим.
Додано необов’язковий фільтр `currency=UAH|EUR`; без нього береться поточна
валюта ресторану. Відповіді звітів про чайові також містять валюту.

## 6. Працівники

- `DELETE /employees/{id}` — м’яке видалення адміністратором зі збереженням історії.
- `PUT /orders/{id}/employee` з `{"employeeId":3}` — перепризначення відкритого
  замовлення адміністратором.
- Видалення працівника з відкритими замовленнями або останнього активного
  адміністратора повертає `409`. Спочатку перепризначити або закрити замовлення.
- Видалені працівники не потрапляють у звичайний список і не можуть авторизуватися.

## 7. Відгуки після оплати

| Запит | Призначення |
|---|---|
| `GET /reviews/eligibility?paymentId=123` | Перевірити доступність; `data` — boolean; для готівки додати `&token=...` |
| `POST /reviews` | `{"paymentId":123,"rating":5,"comment":"..."}`; для готівки додати `token` у тіло |
| `GET /reviews/invitations/{paymentId}` | Одноразове посилання для готівкового платежу; працівник/адміністратор; повертає `paymentId` і `url` |
| `GET /reviews` | Список із пагінацією для адміністратора |

Для онлайн-оплати потрібні cookies платника. Для готівки — токен із запрошення.
Один відгук на гостя й замовлення протягом 7 днів; оцінка 1–5, коментар
необов’язковий, до 2000 символів. Проблемні, реконструйовані або повернені платежі
не дають права на новий відгук. Існуючі відгуки зберігаються.

Для запрошення потрібна сторінка фронтенду `/review`, яка читає параметри
повернутого `url`. Коментарі відображати як текст.

## 8. Гостьова сесія та формат відповідей

QR-вхід через наявний `GET /dining-tables/guest?uuid=...` замінює застарілі cookies
та приєднує гостя до поточного відкритого замовлення. При повторному відвідуванні
потрібно виконати QR-вхід і заново завантажити замовлення; не покладатися лише
на локально збережений стан попереднього візиту.

Обгортка відповіді залишилася: `success`, `message`, `data`, `errors`.
Пагінація: `data.items` та `data.meta` (`page`, `size`, `total`).
Гостьові запити мають передавати cookies, як і раніше.
